## 2.2.1 Spring Boot 修改示例

你可以把现在的 2.2.1 改成这种：

> 本系统后端需要同时处理预约挂号、医生排班、电子病历管理和权限认证等多个业务模块，各模块之间存在较多接口调用和数据交互，因此后端框架需要具备较好的模块组织能力和接口开发效率。基于这一需求，本文选用 Spring Boot 作为后端开发框架，用于搭建系统的 RESTful API 服务。
>
> 在具体实现中，Spring Boot 主要承担控制层接口接收、业务逻辑处理和服务组件整合等功能。例如，普通用户发起预约挂号请求后，后端需要完成用户身份校验、号源余量判断、挂号记录写入以及相关信息返回等操作。Spring Boot 的自动配置机制能够减少传统 Java Web 项目中大量重复配置，使开发过程更加集中于业务逻辑本身。同时，Spring Boot 与 MyBatis、Redis 等组件具有较好的集成能力，能够满足本系统在数据库访问和身份认证方面的开发需求。
>
> 因此，本文选择 Spring Boot 并不是单纯出于框架流行程度的考虑，而是因为其能够较好地支撑本系统多模块接口开发、业务逻辑组织和后续功能扩展的需要。

这个版本的优点是：它不再只是介绍 Spring Boot，而是说明“为什么你的系统需要 Spring Boot”。

## 2.2.2 MyBatis 修改示例

可以这样改：

> 本系统涉及用户信息、就诊人信息、医生排班、挂号记录和电子病历等多类数据表，部分业务还需要根据用户角色、医生编号、就诊日期和挂号状态等条件进行联合查询。因此，持久层框架不仅要完成基本的数据增删改查，还需要支持相对灵活的 SQL 编写。
>
> MyBatis 采用 SQL 与 Java 方法映射的方式进行数据访问，开发人员可以根据业务需求直接编写 SQL 语句，这使其比较适合本系统中多条件查询和业务关联较多的场景。例如，在挂号记录查询功能中，系统需要根据用户身份筛选对应的预约记录；在医生排班功能中，系统需要根据医生编号、日期和时间段查询可预约号源。使用 MyBatis 可以较为清晰地控制这些查询逻辑，并方便后续根据业务变化调整 SQL。
>
> 与全自动 ORM 框架相比，MyBatis 需要开发人员手动维护 SQL 语句，数据库结构发生变化时维护成本相对较高。但考虑到本系统的数据表关系较明确，且存在较多定制化查询需求，因此 MyBatis 更符合系统的数据访问特点。

这个版本比原文更像论文分析，不像“技术百科”。

## 2.2.3 Vue 修改示例

可以这样改：

> 本系统面向普通用户、医生和管理员三类角色，不同角色对应的页面功能存在明显差异。普通用户侧重预约挂号和病历查询，医生侧重患者信息查看和病历录入，管理员侧重用户管理、排班维护和基础数据管理。因此，前端需要具备较好的组件复用能力和页面状态管理能力。
>
> 本文选用 Vue 作为前端框架，并结合 Vue Router 和 Pinia 实现页面路由与状态管理。在系统实现过程中，预约挂号页面、医生排班页面、病历录入页面和后台管理页面均可以按照功能拆分为相对独立的组件，从而降低页面之间的耦合度。对于登录状态、用户角色和 Token 等公共信息，系统通过状态管理机制进行统一维护，使不同页面能够根据用户权限展示对应功能。
>
> 通过采用 Vue，系统前端能够以组件化方式组织页面结构，减少重复代码，提高页面开发和维护效率。同时，结合 Element Plus 组件库，可以较快完成表单、表格、弹窗和分页等常用界面元素的构建，从而满足本系统对交互性和易用性的要求。

# 三、3.1 各角色需求：减少常识性说明的修改示例

你现在 3.1 最大的问题是：很多句子在解释“注册后才能登录”“医生可以查看排班”“管理员可以管理用户”，这些内容太常识，容易显得水。

建议把“功能清单”改成“角色在业务流程中的作用”。

## 3.1.1 普通用户角色需求修改示例

可以替换为：

> 普通用户是门诊服务流程的发起者，其需求主要集中在预约前的信息维护、预约过程中的号源选择以及就诊后的病历查询。用户进入系统后，需要能够维护本人或家属的就诊人信息，并根据科室、医生和出诊时间选择合适的号源完成预约。由于实际门诊场景中存在为家属代挂号的情况，系统需要支持一个账户关联多个就诊人，以提高预约操作的灵活性。就诊结束后，普通用户还应能够在权限范围内查询个人电子病历和历史诊疗记录，从而提高诊疗信息的连续性和可查性。

这个版本比“（1）用户注册与登录（2）就诊人管理……”更像论文正文。

## 3.1.2 医生角色需求修改示例

可以替换为：

> 医生角色主要承担门诊接诊和病历维护工作，其需求贯穿接诊前、接诊中和接诊后三个环节。接诊前，医生需要查看当天预约患者列表，提前了解患者基本信息和相关病历资料；接诊过程中，医生需要根据诊疗情况录入诊断结果、病情描述和治疗方案，形成结构化的电子病历记录；接诊后，医生还需要对已归档病历进行查询、补充或必要修改，并结合个人排班信息安排后续诊疗工作。由此可见，医生端功能的重点在于提高诊疗记录的规范性和门诊接诊过程的连续性。

------

## 3.1.3 管理员角色需求修改示例

可以替换为：

> 管理员主要负责系统基础数据维护和门诊业务流程管理，是保障系统正常运行的重要角色。与普通用户和医生不同，管理员不直接参与诊疗活动，而是通过维护用户信息、医生账户、科室信息和排班数据来保证预约挂号、病历管理等业务能够顺利开展。在实际运行过程中，管理员需要根据门诊资源变化及时调整医生排班和号源配置，并对异常账户或基础数据进行管理。因此，管理员端功能应重点满足数据维护、权限管理和排班调度等需求。

这三段改完之后，3.1 会明显不像说明书。

# 四、3.2 功能需求分析：可以保留列表，但要减少“该模块主要包括”

3.2 是“功能需求分析”，这里用列表是可以的。但现在每一小节都是：

> 该模块主要包括以下功能：
>  （1）……
>  （2）……
>  （3）……

这种句式重复太多。建议每节开头换成更自然的陈述句。

比如 3.2.1 可以改成：

> 用户管理模块承担系统身份认证和基础信息维护功能，主要服务于普通用户、医生和管理员三类角色。该模块不仅需要支持账号注册、登录认证和权限校验，还需要实现就诊人信息维护和医生账户管理，为后续预约挂号、排班管理和病历查询提供身份基础。

这样就可以不用再分四个小点，或者只保留必要的小点。

3.2.2 可以改成：

> 挂号管理模块是连接患者预约需求和医生排班资源的核心模块。该模块需要支持用户根据科室、医生和时间段完成预约，同时记录预约时间、接诊医生和诊疗状态等信息。当患者无法按时就诊时，系统还应提供取消预约功能，以释放未使用号源，避免资源浪费。

# 五、8.1 研究总结：建议重写，不要重复摘要

你现在 8.1 的问题是：它基本又说了一遍“系统采用前后端分离架构、Spring Boot、Vue、用户权限、预约挂号、医生排班、电子病历”等，和摘要、研究内容、系统实现部分重复度较高。

8.1 应该突出三个东西：

**完成了什么、验证了什么、还有什么不足。**

------

## 8.1 研究总结修改示例

可以直接替换成下面这一版：

> 本文围绕门诊挂号系统与电子病历系统分散运行、门诊排班主要依赖人工经验等问题，设计并实现了一个基于时序预测的门诊挂号与电子病历一体化管理系统。在系统实现方面，本文采用前后端分离架构，完成了用户管理、预约挂号、医生排班、电子病历管理和权限认证等核心功能，使患者预约、医生接诊和病历记录能够在同一系统中完成，初步实现了门诊业务数据的集中管理。
>
> 在数据分析方面，本文基于历史挂号数据构建了 SARIMA 时间序列预测模型，并根据预测结果设计了初步的排班辅助推荐机制。该部分工作使系统不仅能够完成基础业务管理，还能够对未来门诊需求变化提供一定参考，从而为门诊资源配置提供辅助依据。
>
> 通过功能测试和性能测试可以看出，系统各主要模块能够按照预期完成运行，预约挂号、排班维护、病历录入和权限校验等功能基本满足设计要求，预测模块也能够反映挂号量的周期性变化趋势。但同时也应看到，本文系统仍主要基于仿真数据和实验环境进行验证，预测模型对突发因素的适应能力有限，排班推荐也仍处于规则辅助阶段。因此，后续研究仍需在真实业务数据、模型优化和系统安全性等方面继续完善。

这一版的好处是：总结部分有“收束感”，不会像摘要复制。
